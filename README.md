# Session search

A PI WEB plugin that puts one search box across every conversation on this machine. Type a few characters into the **Search** tab and it lists the messages that contain them, newest conversations first; click a result and the conversation opens.

Where the host can open a conversation at a particular message (an optional patch to the web interface adds this), a result lands on the message and marks it briefly. Otherwise the conversation simply opens at the bottom; everything else works the same.

## What it searches

- **Your messages and the assistant's replies** — the ordinary text of each message.
- **Question cards and your answers to them** — the question, the line of context under it, the options offered, and the options you chose.
- **The short notes the transcript shows** — for example "The user submitted answers to your questions", with the answers listed.

It does not search anything the transcript keeps out of sight: reasoning and thinking, tool commands and their output, system prompts, or branches of a conversation you rewound away from. Compaction summaries are skipped too, because they repeat messages that are still there and would produce the same hit twice.

Matching is on text, not words: `roll` finds `rollback`, and `resolvePlug` finds `resolvePluginNavigation`. Case is ignored.

Archived sessions are included and labelled **archived**.

## Using the panel

Type; results appear after a short pause and are grouped by session, with the matching text highlighted and the role of each hit on the left (**you**, **assistant**, **question**, **note**). **Load more** at the bottom of the list fetches the next page. Clicking a hit opens its conversation.

The footer says how the results were produced and how long they took. While the index is being built for the first time, the panel says **Indexing 12/40** and answers from the transcripts instead — slower, and just as complete. **Rebuild index** throws the index away and starts again; it is a normal button, not a repair procedure.

**Time:** in the footer chooses how a session's time is shown. The default is relative — "22 hours ago". Typing a pattern shows an absolute time instead; `%Y-%m-%d %H:%M:%S` gives `2026-11-12 00:49:05`. The dialog lists the tokens. The choice is stored on the machine rather than in the browser, so setting it once holds for every browser, including a phone; another browser picks it up when the page reloads. Hovering a result always shows the exact time, whatever the setting.

## Agent tools (optional)

The same package can give the assistant read access to its own history. The tools are inert unless you add this package to the agent's Pi packages; with the panel alone, nothing changes.

- **`sessions_search`** — search conversation text and get back matching messages with the entry id needed to read more.
- **`sessions_list`** — list conversations, filtered by name, project, folder, last activity or archive state.
- **`sessions_history`** — read one conversation: its last turns, a time range, or around a particular message, optionally including thinking, tool calls and tool output.

They read through the same index the panel uses, only work inside a PI WEB-hosted session, and are read-only: nothing is archived, moved or sent.

## Where it keeps things

Two files in this plugin's own data directory, `$PI_WEB_DATA_DIR/plugin-data/session-search/`:

- `index.sqlite3` — a cache of the transcripts. It is safe to delete at any time.
- `settings.json` — `{"timeFormat": "relative"}`, or a pattern such as `{"timeFormat": "%Y-%m-%d %H:%M:%S"}`. The **Time:** dialog writes it, and it is safe to edit by hand: a hand edit applies on the next page reload, with no daemon restart. A missing file means relative time.

Neither file lives inside the installed plugin directory, so upgrading the plugin leaves both alone.

It is regenerated by itself when it is missing, empty, unreadable, of an older format, or when you press **Rebuild index** — and that is noticed by the background pass as well as by a query, so a file deleted while nothing is searching is replaced within a few seconds. Until the rebuild finishes, searches are answered by reading the transcripts directly, so nothing stops working and nothing comes back empty.

The index is usually larger than a single conversation and smaller than the whole corpus; about 9 MB for 72 MB of transcripts here. That is the cost of substring search, and it is only disk.

## How the index is kept current

The index follows the transcripts on its own. It checks once when the plugin starts and then every five seconds: one cheap look at each session file, and only the files that changed are read, and only from where the last read stopped. Nothing is re-read when nothing changed, and the work happens one file at a time in the background so a search or a conversation never waits for it.

A file that shrank, was rewritten, moved or opened a new branch is rebuilt from the beginning rather than patched, because those are the cases where a cursor cannot be trusted.

## Installing and upgrading

Copy this directory into the pi-web plugins directory (`$PI_WEB_DATA_DIR/plugins/session-search/`), then restart the session daemon and reload the page. From a checkout, `node scripts/install.js <plugins directory>` performs that copy; it refuses to overwrite anything it does not recognise as this plugin. Upgrading is the same two steps. The server half loads inside the daemon, so it is discovered at daemon start; restarting interrupts live sessions, so choose a quiet moment.

The plugin can be disabled like any other in **Settings → Plugins**, and it needs no permissions of its own: it asks the daemon, which already owns the transcripts. It searches the machine it runs on, so a remote machine is searched by its own copy of the plugin.

## Speed

The index answers in milliseconds. The transcript scan that stands in for it reads the whole corpus and takes a few hundred milliseconds here; both paths are bounded so a search cannot pin the machine.

A cold build of a 72 MB corpus took about two thirds of a second, spread across background ticks so it never stalls a conversation.

## If something looks wrong

- **No Search tab.** The daemon has not loaded the plugin yet, or it is disabled. Restart the daemon, reload, then check **Settings → Plugins**.
- **"Search backend unavailable."** The page is running with a session daemon that does not have the plugin — usually a reload after an upgrade without a daemon restart.
- **It says "Indexing" for a long time.** A cold build over a large corpus takes seconds, and the panel keeps answering meanwhile.
- **Something you remember is not found.** Check it against what is searchable above: thinking blocks, tool output and abandoned branches are never found. If it should be there, press **Rebuild index**; if it still is not, the session may be on a machine this plugin does not search.
- **A very long message shows only its beginning in the snippet.** That is deliberate: snippets read at most the first 64,000 characters of a message so a result page stays small. The message is still matched on its whole text.

## Privacy

Everything happens on this machine. The plugin reads the same transcript files the web interface already reads, and the browser talks only to its own session daemon over the existing plugin connection; nothing is sent anywhere else. Anyone who can open this PI WEB instance can search these conversations, because they are already theirs.
